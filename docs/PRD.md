# IRA Native｜产品需求文档（PRD）

> **v0.3 源资料严格复核稿｜2026-11-23｜已合入正式仓库**。本文件描述拟交付的 v1.0 产品，**不代表任何功能已实现、数据已授权或测试已通过**。真实进度只看 `../README.md` 和之后的可重复测试。

## 1. 产品定位与业务边界

**定位**：面向铁路通信工程技术规格与设备清单的**证据驱动辅助核验工具**。在明确资料使用权的前提下，把技术规格文件和一个相关的清单对齐，报告可证明的陈述差异、可比性障碍和证据不足；保留人工复核路径。**它不自动认定实际设备满足规范，不签发正式验收合格结论。**

**首个具体任务**：以 GPON 接入设备的 `OLT/ONU` 类别为切入点，对一份技术规格书和一份设备清单做*类别、配置变体、数量、计数单位、工程范围及少数简单技术约束*的有依据比对。

**特别强调**：`OLT/ONU` 多数时候是**设备类别而非厂家型号**。同类 ONU 可能对应不同 POTS/FE/GPON 配置，且存在按公司、代建/报价范围、站点分组的不同清单。规格书中的数量可能是**参考数量**并受其他文件约束。没有已确认的适用要求时，差异只能报告为信息或待复核，不能报“违规”。

### 1.1 目标用户与价值假设

初步假设用户为设备技术规格编写/审阅者、清单核对者、工程资料管理员；**尚未完成专业用户需求访谈**。预期价值：少漏看表格/脚注；少把不同类别、配置、范围或版本混在一起；让每个疑点能回到原始 PDF/清单行。节约时间、降低错误的能力需真实用户测试后报告。

### 1.2 v1.0 输入与交付

- 输入：一份 PDF 技术规格书、其已有且明确格式的解析产物、一份 CSV/XLSX 设备清单；可选一份**由使用者确认与本技术规格有明确关系**的补遗/变更（没有可用数据时不影响核心 v1 验收）。
- 输出：结构化 `Finding` 列表、左右原始证据、核验规则和版本、`no_issue / issue / informational / review_required / blocked`、不可比较原因、人工审阅记录及 JSON/CSV 导出。
- 界面：同一服务支持 CLI 与本地 Web 核验台；能够查看 PDF **物理页**，可信时高亮块区域，清单端定位 CSV 行或 XLSX 工作表/行。完整 PDF 单元格级高亮不是首版承诺。
- Agent：v1.0 **选定 PydanticAI 的受控单 Agent**，在固定流程产生可补查证据缺口时调用只读工具；能离线运行不含 Agent 的核心核验，不能将 Mock 测试当作真实模型验证。
- 不做：真实工程验收单合规认定、施工图理解、在线设备连接、端到端硬件性能评估、全铁路标准适用性推导、多 Agent 产品架构、通用企业知识库。

## 2. 用户工作流

1. 用户登记资料与用途权限，选择技术规格 PDF/解析产物和设备清单；看见配对是否已经证明、是否允许使用模型。
2. 用户指定 GPON、公司/标段/合同/站点及需比对的设备类别/配置范围；必要时确认 Excel 列映射与设备变体。
3. 系统检索并生成要求候选：带来源页、原文、数值/比较符/单位、要求效力、范围/备注与字段级支持状态。
4. 系统对清单行作类别、配置、计数口径及范围匹配，区分**候选同一项、确认同一项、确认不同项和不确定**。
5. 规则系统根据两侧信息角色选择“要求与声明值核验”或“要求与要求比较”；优先审查能否合法比较，再计算结果，列出差异、参考性提醒、未知项与原文证据。
6. 对可修复的表头/条件/补遗证据缺口，用户可选择启动受控 Agent 补查。Agent 只能提出证据或映射候选，须由固定核验链重算。
7. 用户在本地 Web 核对两侧原文和规则，记录**限定于当前文件版本与证据**的审核意见；导出结构化清单。

### 2.1 两个示例（纯合成，绝非铁路标准指标）

- **强制端口阈值**：已证实“同配置 ONU 端口数至少 8”，清单在同范围内声明 9，规则评估 `satisfied`，处置 `no_issue`；仅证明清单声明满足该阈值，不代表设备现场实测通过。
- **参考数量**：规格书表格中的某范围写 6，但上文明确“供参考、须按施工图确定”，另一份清单写 4；应列为 `informational` 或因最终设计文件未提供而 `review_required`，**不能报工程不合格**。

## 3. 必需功能（v1.0 P0）

| ID | 可观察交付 | 最低验收条件 |
|---|---|---|
| P01 来源登记 | 只读导入 PDF + 解析 JSON + CSV/XLSX | 原始字节 SHA、可访问范围和来源状态可查看；相同输入幂等；缺原件/损坏格式失败清楚 |
| P02 证据检索/回查 | 检索章节、文本、表格、型号/类别词 | 每条返回稳定 Evidence ID、PDF 物理页、块/页精度；不能给不存在的 cell bbox；无结果不等于不存在 |
| P03 表格及字段风险 | 保留 MinerU 原始块、续表标志和原文 | 跨页续行、表头、注释、O/0 等风险可显示；没有可靠单元格来源时拒绝自动升级为确认事实 |
| P04 清单读入 | CSV/XLSX 行级来源，用户确认列映射 | 能识别空值、公式单元格、重复行、范围与数值类型；不得执行公式或宏，保留原值 |
| P05 GPON 实体/配置映射 | OLT/ONU 类型、配置变体、厂商型号、站点/范围、计数口径 | 同类不同配置不能合并；缺厂家型号本身不报错；存在一对多歧义时保留待复核 |
| P06 要求与效力抽取 | 表格/条文要求及相关脚注与条件 | 输出 `mandatory/reference/unknown`、角色、单位、表达式、来源；不能仅靠“应”字决定强制效力 |
| P07 确定性核验 | 要求↔声明值的满足性/不确定性、要求↔要求的约束关系分离 | 已确认条件下 Decimal/Pint/结构化配置计算正确；未确认版本/口径拒判；参考差异不直接告警违规 |
| P08 受控 Agent | PydanticAI 单 Agent、只读工具、Budget/Gap/停止策略 | 具有真实模型调用的**合成**案例与 Mock/故障案例；禁止无授权的数据外发和模型直接写人审/结论 |
| P09 人工审阅与导出 | Web 并排或关联证据视图、CLI、JSON/CSV | 检查双方原文、页/行指针、门槛、审核状态与历史，不用“合格”冒充辅助核验 |
| P10 运行与安全 | 单机安装、API、日志、复现与失败码 | 未经授权的工业 PDF/日志/密钥不入 Public 仓库或 CI；只可从白名单资产 ID 读取 PDF |

## 4. 核心判定状态（引用 `CONTRACTS.md`）

**不可再混淆**：

- 约束↔约束：`equivalent / compatible / contradictory / not_comparable / unknown`，另有严格性方向。
- 约束↔声明值或测量值：`satisfied / violated / not_applicable / undetermined`，并标注 `value_role`（通常是 `declaration`，不能推定为实测）。
- 用户问题清单：`no_issue / issue / informational / review_required / blocked`。
- 证据/来源、适用性和人工审核状态另外保存，不用单一 `verified=true`。

**`issue` 的必要前提**：强制且在该工程范围内适用的要求、明确两侧实体或需求槽位关系、正确的配置和计数口径、已核查的关键字段及有效版本、足够的左右证据。即便满足，也只是“潜在不一致，供工程人员审核”，不是正式违规裁定。

**`no_evidence_found` 不能升级为 `record_missing_confirmed`**，除非另有范围完整性证据。无法确认另一份文件覆盖所有项目时只能说“所导入资料中未找到”。

## 5. 外传与模型使用约束

- 建立三类独立许可：个人项目本地使用、外部模型/服务输入、公开导出/再分发。每项不明即不得执行相应动作。
- 真实铁路文件及其解析文本、截图、模型提示词/工具返回内容、日志均按来源授权处置；**只读 Agent 仍可通过模型调用外泄数据**。
- PydanticAI 作为 Runtime 选定；**不锁定云端模型供应商**，因为个人可用账号、地区、网络稳定性和真实数据传输授权并非已核实条件。默认模型调用禁用；合成资料的授权实验可显式开启。
- 模型不能修改来源、规则、人工确认字段或访问限制。Document 中的指令语句视作低信任资料，不作为 Agent 执行指令。

## 6. 交付门槛与评测层次

**功能验收（发布前必须真实执行）**：

1. 一条完整的**合成**工作流：PDF/解析数据 + 清单 → 证据检索 → 类别/配置绑定 → 至少三种处置（强制差异、参考差异、证据不足）→ Web 两侧来源 → 人审 → 结构化导出。
2. 来源/身份、页码/坐标、跨页/脚注、配置变体、范围、计数单位、版本与缺失信息均有反例测试；关键字段可追溯，不把 `source_candidate` 当工程真值。
3. `tests/fixtures/synthetic/cases.jsonl` 的逻辑金标通过，但**不把它当 PDF 解析或真实工业准确率的证据**。新增加合成 PDF E2E 验收、公开资料验证应分别报告。
4. Agent 在受控合成输入下完成至少 5 项真实模型工具回合；另有工具越权、超预算、无进展、模型停用测试。若运行环境无法连接模型，相关测试标明“未执行”，不得自称 Agent v1 完整通过。
5. 有明确可复现的启动命令、版本锁、公开仓库隐私检查和已知限制报告。

**评价指标（需有基准真值后才可计算）**：关键字段 EM、关键错误召回/误报、证据正确率、拒判率、人工复核时间、推理 Token/费用/时延。报告同时给出任务完成率和**错误确定判断率**，不能只报告总体准确率。

**三组对照**：B0 直接 LLM；B1 同样资料/输入的固定结构化提取 + 确定性核验；B2 B1 + PydanticAI 受控补查。不同模型/检索工具差异应控制或标明。合成、授权内部、公开真实样本分别统计；不能用合成分数证明铁路现场可靠性。

## 7. 项目阶段与非目标

- TASK-001：正式工程底座、来源登记、MinerU 指纹适配、Evidence、检索/PDF 原页、CLI/API 与自动测试。
- TASK-002：GPON 要求/清单提取与对齐、字段级来源与人工列映射。
- TASK-003：属性、口径、适用性与确定性规则、Finding。
- TASK-004：PydanticAI EGA、Web/PDF.js、受限人审与导出。
- TASK-005：完整合成/授权实际 E2E、三基线、风险检查与性能优化。

这是**同一正式系统的连续集成**，不是若干可丢弃 Demo。开发期间持续运行自动化测试，不需要等产品写完才测试。

## 8. 开工前需要外部确认（并非要再讨论选题）

1. TX-03 等实际资料能否用于独立个人项目、本地分析、外部模型及公开再分发（分别确认）。没确认则只用公开可分发的合成样例编码。
2. 是否存在有权使用的对应采购/投标设备清单、设计变更及有效施工图。缺失则只能把合成清单作为产品流程验证，不能宣称在真实工程上完成跨文档核验。
3. 目标机器依赖实际兼容性、模型提供商可用性、真实 PDF 坐标误差和 Agent 增益：**研发期间按测试报告确认**，无需开发前凭空签收。

PRD 保持可演进；若改变“参考/强制、型号、要求/声明角色、证据可用性”定义，须同步修订 CONTRACTS、测试种子与开发任务。
